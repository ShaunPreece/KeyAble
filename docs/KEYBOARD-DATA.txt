KEYBOARD DATA: WHERE IT COMES FROM AND HOW TO ADD A MODEL
=========================================================

The hardest-won part of KeyAble is not the code, it is the data: knowing
exactly which keys each Keychron model has, what they are called, and what the
factory-default assignment of every key is. This file explains where that data
came from and how you would add a keyboard the app does not yet cover.


1. THE TWO KINDS OF DATA
------------------------
KeyAble holds two separate datasets, for two separate jobs.

  A. LAYOUT DATA (which keys exist, and their names)
     Stored in the app as KEYCHRON_LAYOUTS. For each supported model it lists
     every key position (row, column) and the human-readable name to show and
     speak for it ("A", "Left Shift", "Enter", and so on). This is what lets
     the app present a text list of keys instead of a picture.

  B. FACTORY DATASET (the true factory keycode of every key, per layer)
     Stored in the app as FACTORY_KEYMAPS, keyed by the keyboard's USB product
     ID (PID). For each model it holds every layer (usually Mac base, Mac Fn,
     Windows base, Windows Fn; five on a few boards) as a map of "row,column"
     to numeric keycode, plus the encoder (knob) assignments. This is what lets
     "reset to factory" write the correct original value back to each layer,
     instead of guessing. Guessing from a key's label is wrong for the
     bottom-row modifiers: on the Mac layer those positions hold Option and
     Command, while the Windows layer holds the Windows key and Alt on the same
     physical keys, so a label-based reset would corrupt the Mac layer.

Layout data is keyed by a layoutId such as "q6_ansi_knob". Two products share
one only when their firmware puts every key at the same matrix position: boards
that look alike are often wired differently (the wired Q6 and the Q6 Max, or the
Q1 versions 1 and 2, number their keys differently), so each gets its own entry.
The factory dataset is keyed by PID/model, because two boards can share a layout
but ship different factory assignments.


2. WHERE IT CAME FROM
---------------------
Both datasets were derived from Keychron's own public, open sources:

  - Keychron's QMK firmware fork on GitHub, for the wireless Max and Pro
    boards:
      repo:   https://github.com/Keychron/qmk_firmware
      branch: wireless_playground
      commit: 666862cb8123b64a6b96718d739c6203ad99031f
    Factory keymaps are the via keymaps, for example:
      keyboards/keychron/v6_max/ansi_encoder/keymaps/via/keymap.c

  - Mainline QMK, for the wired Q, V and S boards, whose Keychron keymaps live
    there:
      repo:   https://github.com/qmk/qmk_firmware
      branch: master
      commit: a738fad372c1e72e10c47f560c8d167d233416ad
    These boards have no via keymap, so the factory keymaps are the default
    ones, for example:
      keyboards/keychron/q6/ansi_encoder/keymaps/default/keymap.c

    The layer blocks (MAC_BASE, WIN_BASE and the Fn layers) in each keymap.c
    are the authoritative factory assignments. These were parsed into the
    factory dataset. The firmware source itself is not included in this
    repository; fetch the commits above to reproduce or check the data.

  - The B6 Pro runs Keychron's ZMK firmware instead:
      repo:   https://github.com/Keychron/zmk
      branch: keychron_bpro
      commit: c284513085c005edf5f9a52b28c8090cc6ed01d2
    A ZMK keymap holds a behavior per key rather than a keycode. Its factory
    dataset is read from Keychron's released firmware (the .uf2 file), and
    translated the way the keyboard's own VIA support does it
    (app/src/launcher/map_keycode.c), with each key placed by the board's
    overlay, for example:
      app/boards/shields/keychron/b6/uk/keychron_b6_uk.overlay
    DevTools/zmk-firmware.mjs does this; see step 4 of section 4.

  - Keychron's VIA JSON files (the same files the Keychron Launcher and VIA
    configurator load), from Keychron's fork (each board's via_json folder) and
    from https://github.com/the-via/keyboards (v3/keychron). These describe each
    board's physical layout and key positions, and are the second source every
    layout is checked against.

  - Keychron's released firmware binaries, the .bin files on Keychron's
    firmware download pages. These are what keyboards actually run, and they
    can differ from the source: Keychron builds each release from whatever
    commit it chooses, and the source moves on afterwards. Wherever a binary
    exists, the factory dataset holds the binary's codes, and the entry says
    which file they came from. Positions and names still come from the source,
    because a binary holds only numbers in matrix order. On the boards checked
    so far, the binaries differ from the source in three ways:
      - Wireless Max boards: the source has an N-key rollover toggle on Fn+N
        that no released firmware has, and the White versions ship with
        backlight speed keys on Fn+T and Fn+G that the source leaves empty.
      - Wired Q, V and S boards: the released firmware predates QMK's
        renumbering of lighting keys and Keychron's own keys, so those keys
        hold different numbers from the source.
      - K2 Pro and K6 Pro: the released firmware uses QMK's older keycode
        numbering throughout, so layer, lighting and Keychron keys all hold
        different numbers from the source.
    The binaries are not included in this repository; DevTools/firmware-
    binaries.mjs downloads them.

  - The QMK / VIA keycode reference (docs/QMK_VIA_Keycode_Reference.txt).
    This maps human key names to the numeric keycodes the VIA
    protocol writes, and documents the "Any" raw-keycode field, modifier
    wrapper syntax, and the limits of what the protocol can express.

Nothing here was invented or guessed. Every model's data traces back to a
Keychron source file, and the more recently added models were verified
directly against both the VIA JSON and the keymap.c layer blocks.


3. HOW A MODEL IS IDENTIFIED AT RUNTIME
---------------------------------------
When you connect, the browser reports the keyboard's USB product ID (PID). The
app looks the PID up to decide which model you have and therefore which layout
and factory data to use. If a PID has layout data but no factory dataset, the
app still works: reset falls back to a best-effort default rather than a
verified per-layer value. If a PID is unknown entirely, the app cannot help
until the model is added.


4. HOW TO ADD A KEYBOARD
------------------------
At a high level, adding a model is a data task, in this order:

  1. Find the board's USB product ID (PID). Connecting an unrecognised board
     shows its ID on the "Keyboard Not Supported" screen, or read it from the
     model's info.json in the firmware source.

  2. Get the layout. Generate it from the firmware, never by hand:
       node DevTools/layout-from-firmware.mjs entry <pid> <layoutId>
     Each key's matrix position comes from the board's info.json or
     keyboard.json, which QMK builds the keyboard from, and its name from the
     Windows base layer of keymap.c. The script refuses a board whose VIA JSON
     disagrees with its firmware. Reuse an existing layoutId only if the
     generated keys are identical.

  3. Download Keychron's released firmware for the model, where there is one:
       node DevTools/firmware-binaries.mjs fetch <Keychron firmware page URL>
     It takes .bin files and the .hex files of older AVR boards such as the
     Q1 Version 1.
     For a ZMK board (the B Pro series), the .uf2 files instead:
       node DevTools/zmk-firmware.mjs fetch <Keychron B Pro firmware page URL>

  4. Build the factory keymaps of every keyboard and write them into the app:
       node DevTools/build-factory-dataset.mjs check
       node DevTools/build-factory-dataset.mjs write
     check lists every entry that would change and writes nothing; write
     replaces the whole FACTORY_KEYMAPS table between its two GENERATED
     markers. For each keyboard with a layout, the build:
       - reads every layer block of its keymap.c (usually Mac base, Mac Fn,
         Windows base, Windows Fn; a few boards have a fifth, in a different
         order) and the knob map, places each key by the LAYOUT matrix order,
         and converts it to its numeric keycode. It stops on any token it
         cannot convert, and writes nothing.
       - lays the codes from the newest downloaded binary over the source's,
         marking the entry "Shipped firmware". It finds the keymap table in
         the binary from the shape the source predicts. A binary with a key
         outside the layout, or a different knob map, is reported and left
         for a person to look at: firmware-binaries.mjs check --details
         lists every difference.
       - for a ZMK board, takes the whole entry from its firmware, and lists
         any key the board has that the layout lacks.
     A board whose own source has the wrong key positions takes them from
     another board's source (POSITIONS_FROM in the build), and must then
     have its own binary.

  5. Check every keyboard against its firmware and VIA JSON:
       node DevTools/verify-keyboards.mjs --details
     It and the build read the firmware source from sparse clones of the
     commits above, plus the-via/keyboards, in
     ProjectAssets/keychron-firmware-src (see the comment at the top of
     DevTools/keyboard-sources.mjs).

  6. Verify against hardware: connect the real board, confirm keys are named
     correctly, remap one key and reset it, and confirm a full factory reset
     restores the true original values on both the Mac and Windows sides.


5. WHAT THE PROTOCOL CANNOT DO
------------------------------
Some things are limits of QMK/VIA, not of KeyAble, and any remapper hits
them:

  - VIA writes single keycodes per position. Complex behaviours that live only
    in firmware source (tap-hold tuning, combos, custom C code) cannot be set
    over the protocol.
  - The "Any" field accepts raw QMK keycode strings and modifier wrappers, but
    only what the firmware's keycode table already understands.
  - JIS (Japanese) physical layouts are not covered by the current data.

The keycode reference file spells these out in detail. Read it before assuming
a remap is possible.


6. THE SHORT VERSION
--------------------
The data is real, sourced, and verified against Keychron's own open firmware.
Adding a keyboard means generating its layout from the firmware source
(info.json and keymap.c, checked against the VIA JSON), parsing its factory
keymap, replacing the factory codes with those in Keychron's released binary
where there is one, keying the factory data by PID, and testing on the actual
board. No reverse engineering of closed software was involved: the firmware is
GPL-licensed QMK, and the binaries are read only to find a table whose layout
the source already gives.
